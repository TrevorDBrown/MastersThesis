\section{Methodology}
    \par The design and implementation of the DashAR system was handled through iterative development practices via Agile. Each iteration of the project consisted of two week sprints, in which work was identified, evaluated, performed, completed, and/or deferred. The development process formally began on Sunday, August 18th, 2024 with sprint 1, and ended on Saturday, March 29th, 2025 with sprint 16. There were brief interruptions in development for various purposes, from writing this thesis (which was tracked in sprint) to impediments that prevented progress (untracked).

    \begin{figure}[h!]
        \vspace{0.5cm}
        \centering
        \includegraphics[scale=0.25]{./Support/Images/DashAR-SprintBoard.png}
        \caption{Sprint 14 Sprint Board in Obsidian MD}
        \label{fig:dasharsprintboard}
    \end{figure}

    \par Sprints were tracked using the Obsidian \gls{pkb} software \cite{Obsidian2025}. An example of this tracking can be seen in figure \ref{fig:dasharsprintboard}. A community module exists for managing Agile sprint boards. Each sprint consisted of a sprint board, with six swimlanes: To Do, In Progress, On Hold, Testing, Completed, and Rollover. Cards were initially added to the ``To Do'' swimlane, and progressed into the others.

    \par ``To Do'' was designated for cards that were waiting to be addressed. ``In Progress'' contained those cards actively being developed. ``On Hold'' contained cards that were unable to continue further into development, for any number of reasons (e.g. a roadblock prevent further work, waiting on a dependency to be worked on first, etc.) ``Testing'' was for cards that had been fully implemented, but needed verification of their functionality against the rest of the system. ``Completed'' contained the cards that were fully implemented and incorporated into the system. Finally, ``Rollover'' contained the cards that were to move into the next sprint.

    \par On Saturdays, cards not in the ``Completed'' swimlane were reviewed to verify their readiness. If a card was completed by the end of the day, it was moved into ``Completed''. If a card was not fully completed by the end of the day, it would be moved into ``Rollover'', to be worked on next sprint. If for any reason a card was no longer needed (e.g. a planned feature ultimately not included in the system, erroneous cards like duplications, etc.), it would be moved to ``Completed'', and the text ``(CANCELLED)'' would be prepended to the title of the card.

    \par Each card had a corresponding Markdown file, which contained more details regarding the work. The sections of the Markdown file were: Tasks and Updates. ``Tasks'' were the step-by-step items needed to complete the overarching work item. ``Updates'' were anecdotal notes, grouped by date, with information assisting with development. An entry was added to Updates for each new cards, signifying the date in which the card was introduced. This helped with tracking the amount of time a card took to get from ``To Do'' to ``Completed''.

    \par Some cards merited implementation that could not be achieved during the development of the system. The title of those cards were prepended with ``(FUTURE WORK)'', to signify their usefulness to the system. An example early on in development of this was the ``Determine uninterrupted power supply issue solution.'' This work item was designed to address a problem faced with the \gls{das} device immediately losing power as soon as the car was turned off. Since the \gls{das} device was a Raspberry Pi, some solutions existed involving batteries (i.e. \gls{ups}) that would help solve the problem. However, it was still not clear of the efficacy of those solutions, as they were bulky, and the batteries were exposed. After some time, a workaround was advised, suggesting that before the car is turned off, the power button on the \gls{das} device should be pressed. This would safely power down the device, stopping running services, such as the \gls{das} \gls{api}.

\section{The Implementation}
    \par The implementation of the DashAR System, following the Agile methodology prescribed, resulted in a usable software system, which met the defined functional requirements. The following subsections detail the development process for each subsystem. Associated source code can be found in Appendix \ref{appendix:project}.

    \subsection{ICS and the DAS API}

        \begin{figure}[h!]
            \vspace{0.5cm}
            \centering
            \includegraphics[scale=0.25]{./Support/Images/RPi5.png}
            \caption{Raspberry Pi 5, an example of a SBC \cite{SparkFunElectronics2023}}
            \label{fig:rpi5}
        \end{figure}

        \par Following the design specified in \Cref{chap:design}, the first implemented subsystem was the \gls{ics} and \gls{das} \gls{api}. The computing platform selected for the \gls{ics} was the \gls{rpi} 5, manufactured by \cite{RPL2025}. \gls{rpi} 5 is a \gls{sbc}, released in 2023, which meets all of the criteria defined for the \gls{ics}. The \gls{rpi} 5 uses an industry standard, ARM-based processor, operating at 2.4 GHz, with \gls{ram} options between 2 GB to 16 GB. This is comparable to a early- to mid-2010s desktop \glsxtrshort{pc}. It is very compact physically, measuring in at 56mm by 85mm. It contains the necessary connectivity options that make it a feasible option for the \gls{ics}, as it can interface with the automobile via a serial-to-\gls{obdii} adapter, either wired (i.e. \gls{usb}) or wireless (i.e. Bluetooth). Regarding energy consumption, the \gls{rpi} 5 consumes around 12 watts of power over a \gls{usb}-C cable, requiring 5V/5A \gls{dc}.

        \par For the DashAR System, a memory configuration of 8 GB of \gls{ram} and 256 GB of storage via a micro \glsxtrshort{sd} card, was selected as the ideal specification to meet the needs of the application. The Ubuntu Server 24.04 \gls{os} was installed on the device. Additional software packages were installed in order to prepare the device to run the \gls{das} \gls{api} service. Specific details regarding the configuration of the \gls{ics} device can be found in Appendix \ref{appendix:build}.

        \par Once the \gls{ics} device was ready, the implementation process could begin for the \gls{das} \gls{api}. The Python programming language, specifically version 3.12 \cite{PSF2025}, was selected as the language to be used for all server-side programming. While lacking some of the robust and low-level features available in traditional systems languages (e.g. C, C++, Rust, etc.), Python was selected due to its platform independence (i.e. ability to run on Linux, macOS, and Windows), its ease of use when implementing functionality, its turnaround time for prototyping, and its ability to be performant enough to execute the tasks it needed. Given the integrations with \gls{obdii} and the real-time nature of this application, it would have been optimal, from a performance perspective, to select a traditional systems language. However, the learning curve for those languages is much higher, and many functions readily available in Python would have to be manually implemented in those languages.

        \par With the programming language selected, the \gls{das} \gls{api} could be developed. The two most important components that made this \gls{api}, let alone the entire project, possible are the python-obd module and the Tornado web server. \cite{Whitfield2025}'s python-obd module provides the facilities for interfacing with \gls{obdii} in software. This module allows for \gls{obdii} interfacing customization, as it provides parameters for setting the baud rate (ranging from 9,600 to 115,200 \gls{bps}), a specific interface device (e.g. /dev/ttyUSB0 in Linux/macOS, COM1 in Windows), and additional operational configurations (e.g. optimized commands, timeouts, voltage check, low power mode, etc.)

        \par The Tornado web server, developed initially by FriendFeed: a social media feed aggregation company, which was acquired by Meta (formerly Facebook) in 2009, is an asynchronous web framework \cite{TornadoAuthors2025}. There were many candidates for this component of the system, such as the Django and Flask frameworks. However, Tornado stood out for its ability to handle concurrency and latency in a performant way. Additionally, it has proven useful in many real-time applications, such as social applications and gaming.

        \par In addition to these two modules, the following modules are also utilized in various ways:

        \begin{itemize}
            \item os: for interfacing with the \gls{os} functions, like file system manipulation.
            \item json: for parsing and storing configurations.
            \item argpase: for passing command line arguments in on script start. For example, enabling verbosity for debugging purposes.
            \item asyncio: for establishing an event loop and asynchronous functionality, mainly for Tornado's HTTP listeners. This is how Tornado achieves its concurrency.
            \item random: for generating random values, namely when the system is in test mode.
            \item enum: for establishing Enums defining lists of values for a given variable. For example, a SystemStatus enum representing the system's states.
            \item uuid: for generating randomized, UUID-compliant values. These values are assigned as IDs for any and all object within the system.
            \item sqlite3: for interfacing with a SQLite3 database.
            \item importlib: for importing custom extensions for DashAR.
        \end{itemize}

        \par Furthermore, custom modules were developed and stored under a directory called ``das\_core'', which represented the greater module of functionality:

        \begin{itemize}
            \item obdii\_interpreter.py
            \item helper.py
            \item data\_connector.py
            \item configuration.py
        \end{itemize}

        \par The first section of code implemented for the \gls{das} \gls{api} was das\_service.py, found in Appenix \ref{scl:dasservicepy}. This module is the main entry point for the application, and is stored in the root of the \gls{das} directory. The initial version of this file contained very basic GET request handling, used to help learn how the Tornado framework works. Once it was determined how Tornado functions, alongside the asyncio module, basic \gls{obdii} data access and storage was developed, as obdii\_interpreter.py. This file can be found in Appendix \ref{scl:dascoreobdiipy}. When the script started, the \gls{obdii} context would be established. Then, the automobile's \gls{vin} would be retrieved. Within the SQLite3 database on device, a record would be written to DASHAR\_SESSION, indicating a new DashAR session was starting. DASHAR\_SESSION would store the \gls{uuid}, which uniquely represented the session, the \gls{vin} of the automobile, and the current date and time, represented as a UNIX timestamp. Once initialization succeeded, an endpoint was accessible to retreive the \gls{obdii} data: /data/obdii. When called, this endpoint would retrieve speed, RPM, and fuel level data over the ELM327 interface via the python-obdii module. This data was written to the DASHAR\_SESSION\_DATA table in the SQLite3 database. DASHAR\_SESSION\_DATA contained a key reference back to the DASHAR\_SESSION table, along with another timestamp, as UNIX timestamp, for when the data points were collected, and the data points themselves. Of note, the DashAR System is designed to be client-side event-driven, meaning the data is only logged when a request is made to the system.

        \par After some time, it was found that some code needed to be reused in multiple places throughout the \gls{das} \gls{api}. Therefore, helper.py was created to serve the rest of the \gls{das} \gls{api} as its namesake suggests: a general helper. This module can be found in Appendix \ref{scl:dascorehelperpy}. helper.py contains shared functions (e.g. UUID generation, UNIX timestamp generation, and Python dictionary to JSON conversion), prepared database statements (e.g. queries, insert statements, etc.), and enums representing the system statuses (i.e. NOT STARTED, STARTING, FAILED, and READY), the service modes (i.e. PRODUCTION, TEST, DEBUG, and INVALID), and other basic lookups (e.g. data formatting, data sources, etc.)

        \par A specific module was developed for handling database transactions: data\_connector.py. This module is responsible for establishing a SQLite3 context, which makes the writing of records to the SQLite3 database possible. Additionally, this module would be responsible for handling file system manipulations (e.g. writing and reading configuration files, writing logs, etc.), However, due to time constraints with the project, this particular functionality was never realized, at least within this module.

        \par Finally, it was realized that customization to the \gls{das} \gls{api}'s data sources and configuration would be necessary. Therefore, the configuration.py module was developed. It can be found in Appendix \ref{scl:dascoreconfigpy}, with an example configuration file in Appendix \ref{scl:configjson}. This module handles the parsing of the configuration file, and tests the configuration for any conflicts. For example, it verifies that the SQLite3 database exists at the specified location on disk. If not, the system will report the error back via the \gls{ics} device's console. Ideally, in the future, this kind of error reporting would be sent to the \gls{hud} application, assuming a connection can be established between the \gls{ics} device and the \gls{ar} subsystem device.

    \subsection{HUD}
        \par After the \gls{das} \gls{api} was in a usable state, the \gls{ar} subsystem was developed. An \gls{ar}-oriented display was chosen as the target output platform because it would allow the \gls{hud} to be superimposed in the user's line of sight while they operate the automobile.

        \par Regarding the development tools available around \gls{ar} development, the Unity Engine was the ideal choice \cite{UnityTechnologies2025}. At the time of design, Unity Engine 2022.3 was the available \gls{lts} version available. Since then, a newer LTS version was released: Unity 6 (or 6000, to keep compatibility with the previously used versioning scheme.) Additionally, XREAL provides an easy-to-use \gls{sdk}: NRSDK, which allows 3D scenes within Unity to be compiled for XREAL \gls{ar} glasses \cite{XREAL2024}.

        \par To achieve a truly customizable \gls{hud}, two configuration files, defined in \gls{json}, are used. The base.json configuration, as shown in Appendix \ref{appendix:hudbaseconfigjson}, defines the general positions of the trays and tray anchors. Additionally, a palette of base widgets are defined. These base widgets, Circles (Small and Large) and Rectangles (Large), provide a means of display critical and non-critical information while operating the automobile. The actual widget definitions refer to these base widgets in order to know how they need to be formatted. The default.json configuration, as shown in Appendix \ref{appendix:huddefaultconfigjson}, define the widgets to be used, their target tray anchor, and their data source.
